## ৩. সনাক্তকৃত ত্রুটিসমূহ (Confirmed Code-Level Bugs)

### ৩.১ Bug 1: `SUPABASE_URL` মিসিং হলে ভ্যালিডেশন ফেইল-ওপেন হওয়া
- **ফাইল:** `backend/services/project_service.py` (`activate_reader`)
- **সমস্যা:** কোডে লেখা ছিল:
  ```python
  if configured_url and submitted_url.lower() != configured_url.lower():
      raise ApiError(...)
  ```
  যদি সার্ভারের `.env`-এ `SUPABASE_URL` কনফিগার করা না থাকে (`configured_url = ""`), তবে শর্তটি মিথ্যা হয়ে যেকোনো নন-এম্পটি সাবমিটেড URL গ্রহণ করে নিচ্ছিল। এটি ফেইল-ক্লোজড (Fail-Closed) নীতি লঙ্ঘন করে।

### ৩.২ Bug 2: মেয়াদোত্তীর্ণ কি (Expired Key)-এর স্টেটাস রোলব্যাক হয়ে যাওয়া
- **ফাইল:** `backend/services/project_service.py` (`activate_reader`)
- **সমস্যা:** কোডে মেয়াদোত্তীর্ণ কি সনাক্ত হলে ট্রানজ্যাকশনের মধ্যে আপডেট চালানো হতো:
  ```python
  cursor.execute("UPDATE reader_keys SET status = 'expired' WHERE id = %s", (key_id,))
  raise ApiError(410, "KEY_EXPIRED", "Reader key has expired.")
  ```
  কিন্তু `raise ApiError` হওয়ার কারণে `backend/db.py`-এর ট্রানজ্যাকশন ম্যানেজার পুরো ট্রানজ্যাকশনকে **রোলব্যাক** করে দিত! ফলে ডেটাবেসে কি-টি পুনরায় `status = 'generated'` অবস্থায় থেকে যেত।

### ৩.৩ Bug 3: কনকারেন্ট অ্যাক্টিভেশন রেস কন্ডিশন ও র' এক্সেপশন লিকেজ
- **ফাইল:** `backend/services/project_service.py` (`activate_reader`)
- **সমস্যা:** 
  1. প্রজেক্টে ইতিমধ্যে কোনো সক্রিয় ইনস্টলেশন আছে কি না, তা ট্রানজ্যাকশনের বাইরে চেক করা হচ্ছিল।
  2. ট্রানজ্যাকশনে `nexora_projects` রো-লেভেলে লক করা হচ্ছিল না (`FOR UPDATE` ছিল না)।
  3. একই প্রজেক্টের জন্য দুটি সমসাময়িক রিকোয়েস্ট আসলে ইউনিক ইনডেক্স ভায়োলেশন (`ux_reader_installations_project_active`) ঘটত এবং ক্লায়েন্টে র' ডেটাবেস এরর (HTTP 500) ফাঁস হতো।

## ৪. বাস্তবায়িত কোড পরিবর্তনসমূহ (Changes Made)

`backend/services/project_service.py` ফাইলে নিম্নলিখিত সংশোধনগুলো প্রয়োগ করা হয়েছে:

### ৪.১ Database URL ভ্যালিডেশন কঠোরকরণ (Contract Enforcement)
- **কন্ট্রাক্ট স্পেসিফিকেশন:** রিডার অ্যাপ শুধুমাত্র পাবলিক Supabase Project URL (`https://<project-ref>.supabase.co`) সাবমিট করবে। কোনো ডিরেক্ট PostgreSQL কানেকশন স্ট্রিং, ডাটাবেস পাসওয়ার্ড বা সার্ভিস রোল কি সাবমিট করবে না।
- **Fail-Closed প্রয়োগ:** সার্ভারে `SUPABASE_URL` কনফিগার না থাকলে সরাসরি `HTTP 503 SERVER_CONFIGURATION_ERROR` প্রদান করা হচ্ছে।
- **PostgreSQL DSN ব্লক:** ক্লায়েন্ট যদি `postgres://` বা `postgresql://` সাবমিট করার চেষ্টা করে, তবে `HTTP 400 INVALID_DATABASE_URL` এরর দেওয়া হচ্ছে।
- **প্লেসহোল্ডার ব্লক:** `change-me`, `example`, `<your-project>` ইত্যাদি প্লেসহোল্ডার থাকলে `HTTP 400 DATABASE_URL_MISMATCH` উত্থাপিত হচ্ছে।
- **সেফ নরমালাইজেশন:** ট্রেইলিং স্ল্যাশ (`/`) এবং কেস-ইনসেনসিটিভ মিল যাচাই করে বৈধ URL গ্রহণ করা হচ্ছে।

### ৪.২ Expired Key ট্রানজ্যাকশন সেফটি নিশ্চিতকরণ
- ট্রানজ্যাকশনের ভেতর `UPDATE reader_keys SET status = 'expired' WHERE id = %s` কার্যকর করার পর কোনো এরর রেইজ না করে ট্রানজ্যাকশন স্বাভাবিকভাবে সমাপ্ত হতে দেওয়া হয়।
- ট্রানজ্যাকশন সফলভাবে **কমিট** হওয়ার পর ফ্ল্যাগ চেক করে ক্লায়েন্টকে `HTTP 410 KEY_EXPIRED` রেসপন্স পাঠানো হয়।
- ফলে ডেটাবেসে কি-এর স্ট্যাটাস স্থায়ীভাবে `expired` হিসেবে সংরক্ষিত থাকে এবং কোনো অবস্থাতেই আর ব্যবহার করা যায় না।

### ৪.৩ কনকারেন্ট অ্যাক্টিভেশন ও প্রজেক্ট রো লকিং
- অ্যাক্টিভেশন ট্রানজ্যাকশনের শুরুতে `SELECT id, status FROM nexora_projects WHERE id = %s FOR UPDATE` প্রয়োগ করা হয়েছে।
- লকের আওতায় `reader_installations` টেবিল পুনর্যাচাই করা হচ্ছে।
- ডেটাবেস ইউনিক ভায়োলেশন ক্যাচ করতে `is_unique_violation(exc)` ব্যবহার করা হয়েছে, যা যেকোনো কনকারেন্ট রেস কন্ডিশনকে সুরক্ষিত ও মার্জিত `HTTP 409 ACTIVE_INSTALLATION_EXISTS` রেসপন্সে রূপান্তর করে। কোনো র' ডাটাবেস এক্সেপশন ফাঁস হয় না।
- ব্যর্থ অ্যাক্টিভেশনে কি কনজিউম হয় না; সফল অ্যাক্টিভেশনে কি স্থায়ীভাবে `used` থাকে।
